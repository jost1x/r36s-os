# Revisión inicial de Armbian y RK3326

**Fecha:** 2026-10-23  
**Fuentes locales consultadas:** `armbian/build` commit `4c0583c6b4786d6948664bd95b3b1000078f96de`; `u-boot/u-boot` commit `870b5d5a21fb6494e82cd9cc1a3dfc8e244d4c20`; `torvalds/linux` commit `734bef548a96e8774d6eef5dfa2026c6edc4e80`; fork fuente R36S U-Boot commit `afcfed9c686cb8fe90b683050a83e1f62a04e818`. Los checkouts de comparación están en `/tmp`; el proyecto fija la fuente y commit, y no incorpora un binario externo de U-Boot.

**Actualización de investigación:** se añadió un perfil de placa experimental, patches de kernel específicos y un script aislado de Armbian. Una revisión anterior de la imagen llegó a terminal por Wi-Fi/SSH en la unidad observada; otra build arrancó dos veces, pero falló el generador Netplan con `match: {}`. La imagen candidata actual asigna el nombre `wlan0`, incorpora provisioning local, detección DC RK817 por GPIO y habilitación del MOTD dinámico. Pasó la verificación offline; aún falta probar esta revisión en consola. El perfil se limita a la R36S observada con configuración de software Panel 4.

**Seguimiento del flujo de arranque:** se compararon los archivos FAT empaquetados y el comando de kernel activo de ArkOS mediante SSH de solo lectura. La imagen Armbian contiene `boot.scr`/`boot.cmd`, `armbianEnv.txt`, kernel, initramfs y DTB R36S Panel 4; el UUID de `rootdev` coincide con el ext4 de la propia imagen. El detalle, incluidos UART y diferencias con ArkOS, está en [Comparación del flujo de arranque](boot-flow-comparison.md). Esta comprobación es estática; no valida el arranque físico ni la cabecera UART.

## Resultado de la búsqueda de placa

- En el snapshot actual de Armbian no hay definición R36S/R35S/RK3326 en `config/boards/` ni familia RK3326 en `config/sources/families/`.
- La familia `rockchip64` declara ARM64 y configura kernel `current` como 6.18. Su helper común configura el kernel actual, pero la selección de arranque Rockchip solo tiene casos específicos para otros SoC; no aparece un caso `rk3326`.
- La configuración de kernel `linux-rockchip64-current.config` activa `ARCH_ROCKCHIP`, MIPI-DSI Rockchip, `ELIDA_KD35T133`, DRM Rockchip, Lima/Panfrost, charger RK817 y codec RK817. No tiene una opción `BATTERY_RK817` en esta versión; el driver `CHARGER_RK817` expone el power supply de batería/cargador. La configuración base no activa `NEWVISION_NV3051D`; el hook propio lo habilita como módulo para el perfil Panel 4.
- Esa configuración no contiene una opción para el controlador vendor `odroidgo3-joypad` observado en ArkOS. La ruta mainline probable para entrada es describir GPIO y joysticks ADC con drivers genéricos, pero las asignaciones eléctricas del R36S deben verificarse antes de escribirlas.

**Conclusión:** el kernel Rockchip64 actual parece tener una base útil para RK3326 y el compatible declarado por esta consola. Armbian no ofrece una receta upstream completa para R36S/RK3326. El proyecto ahora compila un perfil R36S de U-Boot desde fuente, pero el build exitoso no demuestra que el `BOOTCONFIG` arranque en esta unidad ni identifica el entorno persistente del U-Boot ArkOS instalado.

## U-Boot R36S desde fuente

Se encontró y auditó el fork público [AndreRenaud/u-boot-r36s](https://github.com/AndreRenaud/u-boot-r36s), basado en U-Boot v2024.04. El commit fijado es `afcfed9c686cb8fe90b683050a83e1f62a04e818`. Frente al tag oficial v2024.04 añade un `r36s_defconfig`, el target `TARGET_R36S`, un DTS de placa y su DTS de fase U-Boot; el DTS declara SPDX `(GPL-2.0+ OR MIT)`. No se utiliza el release binario de terceros.

El `r36s_defconfig` compilado establece `CONFIG_DEFAULT_DEVICE_TREE="rk3326-r36s"`, `CONFIG_TARGET_R36S=y`, `CONFIG_BOOTCOMMAND="bootflow scan"`, `CONFIG_BOOTSTD_DEFAULTS=y`, `CONFIG_BOOTMETH_SCRIPT=y`, `CONFIG_LEGACY_IMAGE_FORMAT=y`, `CONFIG_MMC_DW_ROCKCHIP=y`, `CONFIG_DOS_PARTITION=y`, `CONFIG_FS_FAT=y`, `CONFIG_ENV_IS_IN_FAT` para `1:1`, consola configurada a 1.5 Mbaud y debug UART base `0xFF160000`. El parche propio [`0001-r36s-boot-from-sdmmc.patch`](../config/armbian/patches/u-boot/r36s/0001-r36s-boot-from-sdmmc.patch) incorpora `rk3326-r36s-u-boot.dtsi`: asigna `mmc0` al lector SD `ff370000`, deja eMMC `ff390000` como `mmc1` y configura SD como única fuente SPL. El método de scripts busca `boot.scr.uimg` y luego `boot.scr` en las rutas por defecto `/` y `/boot/`; la imagen coloca `boot.scr` en la raíz FAT, y el verificador confirma su estructura de script legacy y la coincidencia con `boot.cmd`. Por tanto, configuración, ruta y formato concuerdan estáticamente. `CONFIG_BOOTSTD_FULL` no está habilitado; en esta compilación `bootflow scan` sigue disponible y arranca el primer flujo encontrado, sin las funciones ampliadas de listado/menú. Esto todavía no valida que la consola enumere su lector SD ni que el scan funcione en placa. Incluye SPL/ATF y la receta de Armbian `binman-atf-mainline`. El `.config` desactiva `CONFIG_VIDEO_ROCKCHIP` y `CONFIG_VIDEO_MIPI_DSI`; no esperamos pantalla durante el splash de U-Boot, solo después del inicio del kernel.

**Corrección de auditoría (2026-10-23):** el DTS PX30 genérico identifica `ff390000` como eMMC y `ff370000` como SD; una revisión anterior de este documento los interpretó al revés. El parche de placa fue aplicado por Armbian y la compilación real de `u-boot.dtb` y `spl/u-boot-spl.dtb`, decompilados con `dtc`, confirma en ambos `/aliases/mmc0 = /mmc@ff370000`, `/aliases/mmc1 = /mmc@ff390000` y `/chosen/u-boot,spl-boot-order = /mmc@ff370000`. El verificador también confirma que el binario U-Boot dentro de la imagen coincide con el paquete producido por este build. Esto verifica la configuración compilada, no que el controlador inicialice físicamente la tarjeta en esta unidad.

El TPL ocupa 10116/10240 bytes (98 %), por lo que el margen sigue siendo estrecho. Auditoría adicional del artefacto fuente: no incluye blob DDR propietario. `CONFIG_ROCKCHIP_EXTERNAL_TPL` está apagado; el TPL PX30 compilado llama a `sdram_init()` y, al no seleccionar `RAM_ROCKCHIP_DDR4/LPDDR2/LPDDR3/LPDDR4`, el driver incluye su tabla de la familia DDR3 a 333 MHz por la rama `#else`. El tipo físico de esta unidad no se ha leído. DDR3L es una variante DDR3 de bajo voltaje; LPDDR3 requiere la tabla LPDDR correspondiente. No asumir que el nombre DDR3L basta para certificar los requisitos de tensión/timing de la placa: consultar [`boot-flow-comparison.md`](boot-flow-comparison.md) e identificar el chip. La cabecera UART física tampoco está confirmada. No ejecutar `saveenv`/`fw_setenv`; el comportamiento del entorno de ArkOS sigue sin determinarse.

El primer candidato con `odroid-go2_defconfig` fue un baseline de comparación, SHA-256 `4714fc3e827f6016cfe09c4380a045c7370d0eafbd5acd23fadf8cc0955254d7`; su archivo `.img` se eliminó el 2026-10-24 para liberar espacio. No se escribió a ninguna tarjeta.

## Device trees upstream cercanos

- Linux mainline contiene `rk3326-odroid-go2.dts`, `rk3326-odroid-go2-v11.dts` y `rk3326-odroid-go3.dts`.
- El DTS ODROID-GO2 declara el panel `elida,kd35t133`, coincidente con el compatible observado en el árbol vivo del R36S.
- El DTS ODROID-GO3 describe otro panel (`elida,kd50t048a` / `sitronix,st7701`) y otros detalles de botones/joystick; el nombre `odroidgo3` en el DTB ArkOS no hace a la R36S eléctricamente idéntica al ODROID-GO Super.
- Son puntos de partida para contrastar bindings y drivers mainline. No copiar un DTS de ArkOS ni adoptar el DTS de ODROID sin verificar diferencias del panel, batería, GPIO y joystick.

## Hallazgo bloqueante: panel mainline

El driver Linux mainline `panel-elida-kd35t133.c` usa una secuencia de inicialización genérica del fabricante, pero su `default_mode` está fijado en **320×480**, 17 MHz, con área física 42×82 mm. El panel ArkOS activo en esta unidad opera a **640×480**, 29 MHz, y declara 52×70 mm. Aunque el compatible coincide, el modo, geometría y programación no coinciden. El DTS ODROID-GO2 solo añade compatible y reguladores al nodo de panel; no resuelve estas diferencias.

Por tanto, el controlador mainline no es reutilizable tal cual para la unidad observada. Se encontró un DTS R36S y driver de Andre Renaud bajo licencias GPL/MIT, guardados/auditados en `device-trees/reference/` y en las referencias de la auditoría. Los 153 registros principales coinciden exactamente con el Panel 4 de ArkOS; el comentario del driver dice que la secuencia fue suministrada por el fabricante pero no identifica la fuente. El patch conserva la licencia/atribución y emite los comandos finales DCS mediante helpers del kernel. El ID físico del panel sigue sin leerse. El DTB ArkOS local se conserva solo como evidencia porque su licencia no está resuelta.

Fuente: [driver mainline panel-elida-kd35t133.c](https://github.com/torvalds/linux/blob/734bef548a96e8774d6eef5dfa2026c6edc4e80b/drivers/gpu/drm/panel/panel-elida-kd35t133.c).

## Prototipo de placa Armbian

La auditoría del framework confirma puntos de extensión bajo `userpatches/config/boards/` y `userpatches/kernel/`. El proyecto contiene `config/armbian/boards/r36s.wip`, el patch propio `r36s-6.18`, un hook de config del kernel y `scripts/build-armbian.sh`, fijados al commit de Armbian indicado al comienzo de este documento. El perfil resuelve a `rockchip64`, kernel `current` 6.18 fijado ahora al commit `2926d88bb7fc4608fd942453d929c39e4e5ec006`, U-Boot R36S v2024.04 en el commit indicado, `BOOT_SOC=px30`, TF-A `PLAT=px30` y `binman-atf-mainline`. Antes de este ajuste, Armbian resolvía el kernel desde la rama móvil `linux-6.18.y`. El kernel instala el DTB R36S Panel 4 y el módulo NV3051D adaptado a 29 MHz y 640×480. El bootloader sigue pendiente de prueba por UART/microSD.

Se eligió `binman-atf-mainline` después de comprobar que el escenario `blobless` intentaba invocar objetivos que no existen en el U-Boot investigado. Se confirmó el empaquetado binman upstream tanto con ODROID-GO2 v2026.10 como con el fork R36S v2024.04. La imagen activa usa el fork R36S y el paquete `linux-u-boot-r36s-current` compilado desde su código fuente.

El build queda repetible con los commits fuente fijados, pero no es bit a bit reproducible: los índices/repositorios Debian y paquetes base son móviles, y la imagen recibe un UUID ext4 nuevo en cada generación. El framework fijado elige su contenedor principal con la etiqueta móvil `trixie-latest` y vuelve a descargarla cuando vence el marcador de 24 horas. Para reducir esa variación sin editar el checkout de Armbian, `scripts/build-armbian.sh` actualiza al inicio la etiqueta que el framework espera hacia el digest revisado `ghcr.io/armbian/docker-armbian-build@sha256:bffb2b34becdefe1d13872a02455f5044c9ba200b8543a2e7fb19fbf33e9009a`; el wrapper `scripts/docker-compat/docker` también redirige cualquier pull posterior de esa etiqueta al mismo digest y la vuelve a etiquetar localmente. En el host de build, Docker reporta ese digest para `armbian-debian-trixie-latest`. Se comprobó la redirección invocando el wrapper con `docker pull` sobre esa etiqueta y luego inspeccionando el resultado: el ID local `sha256:bab47412a076ae4df3102290de62cb00854247d6b1801b2deffe72848641e309` expone el RepoDigest fijado. La referencia por digest evita que una etiqueta que cambie en el registro sustituya silenciosamente la imagen base durante un build. Este pin mejora la repetibilidad del entorno, pero no fija Debian/APT ni crea una imagen bit a bit idéntica. El build del 2026-10-23 se repitió después de añadir el pin y terminó correctamente; su log es `work/armbian-build/output/logs/log-build-d969f91c-87e0-402c-a667-6938987b6c57.log.ans`. Véase [`docker.sh` en el commit Armbian fijado](https://github.com/armbian/build/blob/4c0583c6b4786d6948664bd95b3b1000078f96de/lib/functions/host/docker.sh).

El build integral de Armbian se completó en el host local después de resolver tres problemas del entorno: Docker/runc requería un `nofile` explícito, el contenedor Trixie almacena los registros QEMU en el formato nuevo `systemd-binfmt` mientras esta revisión de Armbian usa `update-binfmts`, y el límite de RAM para BTF era ligeramente superior a la memoria que Armbian detectaba. El wrapper de Docker se mantiene en `scripts/docker-compat/`; el proyecto incluye una extensión/shim de compatibilidad acotada al contenedor de build y desactiva BTF (`KERNEL_BTF=no`). El perfil también instala `python3-pyelftools` y `python3-setuptools` para U-Boot/binman. El script retira al terminar solo los handlers QEMU que este build añadió al host; la repetición comprobó que quedan únicamente `register` y `status`. No se escribió ninguna tarjeta ni dispositivo externo.

### Entrada en el kernel de la imagen actual
